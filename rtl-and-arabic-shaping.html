Right-to-Left and Arabic Shaping

Scoped honestly. This page describes exactly what v1 does for right-to-left text, and the Honest Limits page lists what it does not do. Read both before relying on either.

What v1 includes

  • Right-to-left language detection.
  • A compact Arabic presentation-form shaper, with paragraph reversal for single-line UI strings.
  • Direction and alignment helpers that the binding components apply automatically, including an optional automatic alignment flip.
  • Arabic and Hebrew rows in the Hello World Tour sample, so the behaviour can be seen in the included demo (Sample Guide).

Detection

RtlSupport.IsRightToLeft(code) answers from the base language. The set covered is: ar, he, fa, ur, ps, sd, ug, yi, dv, ckb. Regional variants answer through their base language, so a regional Arabic code is treated as right-to-left.

Helpers also answer whether a string contains right-to-left characters, and whether it contains Arabic-script characters.

The Arabic shaper

ArabicShaper.Shape(text) converts logical-order Arabic text into its shaped, visually ordered form for single-line UI use:

  • Letters take their presentation forms according to position.
  • The lam-alef sequence shapes to its single ligature form, in both isolated and final contexts.
  • Diacritic marks pass through unshaped and stay attached to their letters.
  • In a mixed line, non-Arabic runs keep their internal order while the run order of the line is reversed — a line holding a Latin label, an Arabic word, and a number keeps the label and the number readable in place.
  • Text with no Arabic passes through unchanged. Empty input returns empty.

The binding components apply shaping on output when the resolved string calls for it, so labels need no shaping code of their own.

Hebrew

Hebrew needs no shaping. For Hebrew the package provides detection plus direction and alignment handling in the components: the label right-aligns and paragraph direction follows the language. Glyphs themselves come from your font, as with any other language (Fonts and Fallback Chains).

The scope line — do not cross it in your own planning

  • The shaper's coverage is the core Arabic alphabet plus common Persian and Urdu letters, as shipped. Its claim extends as far as the shipped sample demonstrates, and no further.
  • This is not a full UAX#9 bidirectional implementation. Long, multi-paragraph, mixed-direction documents are the platform text stack's job, not this package's.
  • No shaping is provided for scripts beyond Arabic. Detection and direction helpers cover the Hebrew-class scripts listed above; Indic and Thai shaping belong to the platform text stack.

If your game carries long-form mixed-direction documents, plan that text with the platform stack and use this package for what it is built for: spreadsheet-driven UI strings, with single-line Arabic shaped and demonstrated in the sample.
